## 一、项目进展情况

### （一）总体进度

项目于 2025 年 11 月立项，执行期两年。按照申请书拟定的五个阶段，截至目前已完成第一阶段（资料收集、需求划分、概要设计与总体设计）、第二阶段（代码实现）与第三阶段（测试与二次维护开发）的主要工作，并已进入第四阶段的正式运行测试与性能优化。阶段性交付物为可运行的本机单用户 Web 应用“灵谱”（Lingpu），由音频转录、乐谱生成与保存、乐谱阅读、练习辅助、人机协同校正五部分组成，源代码、运行说明与评测记录均在项目仓库中维护。

### （二）钢琴音频转录流水线

系统采用“浏览器—接口服务—独立推理进程”三层结构。后端以 FastAPI 提供 HTTP 接口、以 SQLite 保存任务与曲库，并用单消费者队列串行执行任务。音频解码与模型推理在单独派生的推理进程中进行，既不占用接口服务的请求事件循环，也避免大模型与 Web 服务争抢显存。上传后先用 ffprobe 检查容器、音轨与时长，再用 ffmpeg 解码为 16 kHz 单声道，解码结果再次校验时长。默认模型为 ByteDance 音符与踏板预训练模型，模型缺失或损坏时健康检查报告未就绪。CUDA 失败不会自动退回 CPU。任务状态为排队、运行、完成、失败，阶段为排队、解码、转写、建谱、完成，进度百分比来自模型真实的分段推理。服务重启时未完成任务统一标记为失败，已完成曲目持久保留。上传上限 100 MB、10 分钟，当前面向纯钢琴独奏音频。

### （三）符号化与乐谱生成

推理输出的音符与踏板事件统一为带秒级起止时间的中间表示，包含音高、起音、释音、力度与踏板区间，原始事件另存为事件文件。MIDI 保留演奏时序。MusicXML 按指定 BPM 与拍号量化，默认十六分音符网格，调号按时长加权估计并允许手动覆盖，左右手按音域分界与音高连续性启发式划分，同起同止的同手音符合并为和弦，交错复音划分声部，跨小节与复合时值以连音记谱。建谱参数可在事后调整（BPM、拍号、量化精度、双手分界、调号），重新建谱复用原始事件、不重新推理。首次导出文件另存副本，原始录音与原始事件不被覆盖。

### （四）乐谱工作台与练习辅助

前端基于 Vue 3、Pinia、Naive UI 与 alphaTab 构建。曲库统一管理音频转录曲目与 MusicXML、MXL 导入曲目，支持重命名、下载与删除，导入谱保留原始记谱，刷新或服务重启后仍可继续打开。阅读页为自适应宽度分页，支持点击纸页两侧、滑动与方向键翻页、专注模式、全屏、适应宽度与适应整页，并按曲目记忆阅读小节与缩放，播放或拖动进度时跟随播放位置翻页。练习方面实现合成音与原始录音两种音源（切换时保留时间位置）、左右手分别调音量、0.5 至 2 倍速、A/B 循环、一小节预备拍，以及基于 Web Audio 音频时钟提前调度的机械节拍器（3/4、4/4、6/8，6/8 以附点四分音符为一拍、默认三细分），摆杆与节拍声同源，空格键播放与暂停。导出支持在新窗口按纸张宽度重新排版后打印或保存为 PDF。

### （五）人机协同的音符纠错与局部重转录

针对转录结果需要人工干预的现实，实现了独立的全屏纠错工作台。可在谱面、音符时间图与事件列表中选择音符，增删音符，修改音高、起止时间、时值、力度与左右手归属。修改写入数据库历史，支持跨刷新与跨服务重启的撤销与重做，撤销后再修改会结束原重做分支。局部重转录只把所选片段及前后各 0.75 秒的上下文送入模型，结果先以叠加音符预览，用户确认后才替换。替换范围按音符起点界定，范围外音符保持原有标识与属性，踏板按区间合并。所有写回都带版本校验，页面之间或后台任务之间的过期提交会被拒绝。

### （六）评测、测试与文档

建立三级验证：单模型基准脚本、多模型统一对比套件，以及五组合成参考语料（旋律、双手和弦、重复音与踏板、跨小节长音、静音），识别与建谱分开评估。10 秒真实音频在本机 RTX 5090 D v2 上，ByteDance 模型加载 2.814 秒、端到端 3.679 秒、峰值显存约 340 MB，输出 19 个音符与 4 个踏板区间。Transkun 同片段端到端 11.322 秒、18 个音符。五组合成语料上，建谱回读的起止 F1 均为 1.0。模型识别 onset F1 依次为 0.762、0.696、0.714、0.800、1.000，onset 与 offset 联合 F1 依次为 0.762、0.348、0.143、0.000、1.000。真实钢琴录音目前记录耗时与事件数量，精度指标依赖下一阶段的同次演奏参考标注。工程验证包括后端 32 项 pytest、前端类型检查与 18 项单元测试、生产构建、两套 Playwright 浏览器回归（常规工作台与纠错工作台，均拦截接口、不改动真实曲库），以及 ruff 与 Prettier 格式检查。四份可复现记录与界面截图保存在 docs 目录。

### （七）与申请书指标对照

## 二、存在的问题和不足及拟采取的应对措施

1. 模型仍为公开预训练权重，自主训练环节尚未落地。当前摘要与设计文档均标注默认使用 ByteDance 预训练模型，知识蒸馏与对抗增强仍停留在方案阶段，原因在于标注数据与训练算力尚未就绪，本阶段优先保证端到端可用。措施：先建立真实演奏的人工参考 MIDI 小规模测试集，得到可信基线，再以教师—学生结构做蒸馏可行性实验，仅在音质与体积确有收益时并入主线，时间安排在 2026 年 12 月至 2027 年 3 月。

2. 时序精度不足，释音与踏板最弱。合成语料上 onset F1 尚可（0.696 至 0.800），而 onset 与 offset 联合 F1 在双手和弦、重复音与长音上分别降至 0.348、0.143 与 0.000，说明模型对延音与踏板延长后的释放时刻判断与真实演奏不一致。措施：把 offset 与踏板拆成独立子任务评估，先区分键盘释放与踏板释放两种口径，再用纠错工作台积累的错误样本做针对性调参与微调。

3. 量化与左右手划分属于启发式结果。复杂演奏仍须人工校对，且调整只能通过重新建谱入口完成。措施：整理失败样例改进声部与手别连续性规则，并在界面上标注自动结果的适用范围，便于使用者决定是否复核。

4. 申请书中的移动端与无接触翻页尚未实现。当前是桌面浏览器优先的本机单用户应用，平板与手机只做了响应式收敛。措施：2026 年 12 月至 2027 年 3 月先做摄像头双眨眼检测的可行性原型与交互评审，验证误触发率与演奏干扰后再决定是否并入主干，平板适配按可用性测试结果排期。

5. 算力与经费集中在后半阶段。目前只有单机单卡环境，训练与对比评测必须串行执行，经费尚未报销。措施：训练任务串行排队，评测固定同一音频与设备条件以保证可比性。经费按申请书预算在下一阶段集中用于文献检索与论文出版，并按学校财务流程据实报销。

6. 工程遗留问题尚待清理。alphaTab 上游存在 import.meta 与包体积提示，测试依赖库有弃用告警，长音频与并发场景的运行测试还不够充分。措施：随上游版本升级清理告警，补充长音频、异常输入与并发健康检查的回归用例。
